# 작업 명세 공통 규칙 (Task 3 이후 전 티켓 적용)

- 결정 일자: 2026-09-21
- 결정자: 리드 (사용자 요청 반영)

## 1. 계획서 코드는 "참조 구현"이다 — 그대로 복사할 의무 없음

상위 계획 `docs/superpowers/plans/2026-09-17-kudos-rag-poc.md`의 각 Task Step 코드는 **동작을 설명하는 참조 구현**이다. Builder는 다음을 모두 지키는 범위에서 더 간결하게 작성할 수 있다.

**반드시 지킬 것 (변경 금지):**
- 각 Task 명세(`docs/plans/task-NN-*.md`)의 **인터페이스** — 모듈 경로, 클래스/함수 이름, 시그니처, 반환 타입, 예외 클래스, public 속성, 상수 이름
- 명세의 **동작 규칙** (예: 재시도 횟수·백오프, 매크로 처리 표, metadata 키·타입)
- 계획서 Step 1의 **테스트 코드** — 테스트가 요구하는 계약이 곧 인터페이스다. 테스트를 통과시키기 위해 테스트를 바꾸지 않는다(명세가 명시적으로 허용한 경우만 예외)
- Global Constraints: LangChain import 경로, LLM/임베딩 생성은 `llm_factory` 한 곳, Chroma metadata 타입 제약, 한국어 주석

**간결화 허용 범위:**
- 중복 로직 합치기, 불필요한 중간 변수·분기 제거, 내부(private) 헬퍼 통합·분리
- 참조 구현의 방어 코드 중 테스트·명세가 요구하지 않는 것 제거 (단, 명세의 동작 표에 있는 케이스는 유지)
- 더 단순한 표준 라이브러리 사용

**간결화가 아닌 것 (하지 않을 것):**
- 새 의존성 추가, 설정파일 변경
- 인터페이스를 "더 좋게" 바꾸기 — 필요하다고 판단되면 리드에게 보고하고 대기
- 미래 확장을 위한 추상화·옵션 추가

## 2. 간결화 시 보고 방식

완료 보고에 "참조 구현과 다른 점"을 한 줄씩 적는다 (예: "`_get`의 `last_status` 추적을 예외 메시지 조립으로 단순화"). Validator는 그 차이가 명세의 동작 표를 깨지 않는지 확인한다.

## 2-1. Validator 판정 기준 (2026-09-21 Validator 확인)

- 판정은 명세의 인터페이스·동작 표·완료 기준 충족 여부로 한다. 참조 구현과의 구조 차이는 "비차단 의견"에만 기록하고 판정에 반영하지 않는다.
- 엄격 확인 항목: 모듈 경로·이름·시그니처·반환 타입·예외 클래스·public 속성·상수 이름, 동작 규칙, 계획서 Step 1 테스트 미수정(`git diff`), Global Constraints.
- Builder가 제거한 방어 코드가 **명세 동작 표에 있는 케이스**면 → RETURN TO BUILDER. **동작 표가 그 케이스를 규정하지 않아 판단이 갈리면** → ESCALATE TO LEAD (리드가 명세를 갱신해 결정).

## 2-2. 테스트 작성 책임 분담 (2026-09-21 Builder 질의로 확정)

- **Builder**: 계획서 Step 1 테스트(계약)만 작성한다. 명세 "검증 전략"의 추가 확인 항목을 위한 테스트는 작성하지 않는다.
- **Validator**: 검증 전략 중 계획서 테스트가 덮지 않는 항목을 추가 테스트로 작성한다(기존 테스트 파일에 append, 애플리케이션 코드는 수정하지 않음).
- 이유: 구현자와 검증자가 같은 케이스를 각자 작성하면 중복이고, 구현자가 자기 코드에 맞춘 테스트를 쓰면 검증 독립성이 약해진다.

## 2-2-1. 네트워크 비의존 검증 방법 (Validator, 2026-09-21 정정)

"소켓 차단 상태 통과"는 Validator의 pytest 플러그인이 **AF_INET/AF_INET6 연결 시도**를 `RuntimeError`로 차단한 상태에서 전체 스위트를 실행한 결과를 뜻한다. `socket.socket` 생성 자체는 막지 않는다 — asyncio 이벤트 루프가 self-pipe용 AF_UNIX `socketpair`를 쓰기 때문(Task 10 비동기 테스트에서 발견·정정). Task 1~9 결과는 더 강한 조건(소켓 생성 차단)에서 통과했으므로 유효하다.

## 2-3. 티켓 상태 용어

| 상태 | 의미 |
|---|---|
| 신규 구현 / 진행 중 | Builder 작업 중 |
| ESCALATE | Builder 또는 Validator가 설계 충돌을 보고, 리드 결정 대기 |
| READY FOR REVIEW | 리드 확인 완료: 완료 기준 통과·테스트 green·설계-구현 일치. 리뷰로 넘길 수 있는 상태 |
| 리뷰 N 통과 — 커밋 대기 | 리뷰(사용자 지시로 수행)까지 끝남. 남은 것은 사용자 커밋 |
